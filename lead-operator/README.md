# ТЗ: MVP «ИИ-оператор лидов» (v0.1)

**Контекст:** продукт для малого бизнеса (услуги, Avito-продавцы, салоны). Бизнес теряет лиды, потому что отвечает медленно или не отвечает ночью. Мы строим ИИ-оператора, который отвечает за секунды, квалифицирует лида, записывает и передаёт человеку горячих.

**Цель MVP:** один реальный клиент, один-два канала (Telegram + WhatsApp), стабильный диалог, квалифицированные лиды в карточке, уведомления владельцу. Срок — 1-2 недели.

## Что ВХОДИТ в MVP

1. Приём сообщений из Telegram (Bot API, webhook) и WhatsApp (Green API, webhook).
2. Диалог ведёт LLM (Qwen через DashScope, OpenAI-compatible endpoint; модели qwen-plus / qwen-max).
3. Квалификация лида: услуга, бюджет, срочность, намерение записаться, sentiment, «хочу человека».
4. Запись на слоты (простая сетка слотов из конфига клиента).
5. Эскалация человеку по правилам.
6. Уведомления владельцу в Telegram (карточка лида + транскрипт + алерт о горячем).
7. Конфиг клиента: услуги, цены, FAQ, слоты, тон общения, правила эскалации (в MVP — JSON/YAML файл на клиента).
8. Хранение лидов и транскриптов (PostgreSQL).
9. Docker-compose деплой на VPS.

## Что НЕ входит в v1 (не тратить время)

- Avito (закрытое API) — позже.
- Веб-дашборд — владельцу хватает Telegram-уведомлений; дашборд в v2.
- Биллинг/оплаты — вручную счётом.
- Анти-ноушоу напоминания — это v2 (отдельный апселл).
- Мультиязычность, голосовые.

## Модель данных

- **ClientConfig**: id, name, каналы+кредами, services[], prices{}, faq{}, slots{}, tone, handoff_rules
- **Lead**: id, client_id, channel, contact, status (new/qualified/hot/handed_off/closed), qualification JSON, created_at
- **Message**: id, lead_id, role (user/agent/owner), text, ts

## Логика диалога

Гибрид: LLM ведёт разговор свободно, но после каждого хода — структурированное извлечение (tool call или отдельный JSON-вызов): обновить поля квалификации и при необходимости вызвать действия `book_slot`, `save_lead`, `handoff`.

**Управление памятью (Context Window):**
- Хранить последние N сообщений (например, 10) в полном объеме.
- Для более ранних сообщений хранить краткое резюме (summary) диалога, обновляемое каждые K сообщений.
- Контекст передается в LLM как: `System Prompt + Summary + Last N Messages`.

**Правила эскалации (hard rules, не на откуп LLM):**
- лид прямо просит человека;
- вопрос вне FAQ дважды подряд;
- негативный sentiment;
- бюджет выше порога из конфига (крупная сделка — человеку).

**Этика/легальность:** бот представляется ИИ-ассистентом компании в первом сообщении. Не выдумывает цены/условия вне конфига. Не знает ответа — эскалация, а не галлюцинация.

**UX при задержке:**
- Если генерация ответа LLM занимает > 1 секунды, бот отправляет статус `typing...` (sendChatAction) в соответствующий мессенджер.

## Скелет системного промта

```
Ты — ИИ-ассистент компании «{name}». Отвечай в тоне: {tone}.
Используй ТОЛЬКО факты из: {services}, {prices}, {faq}.
Цель: квалифицировать (услуга, бюджет, срочность) и записать на слот через book_slot.
Если не знаешь ответа или сработало правило эскалации — вызови handoff и мягко передай диалог человеку.
Отвечай коротко (1-3 предложения), без воды.
```

## План сборки (шаги, коммит на каждый)

1. Скаффолд: репо, конфиг, docker-compose (app+pg+redis), модели БД, миграции.
2. LLM-клиент + prompts + qualifier (юнит-тесты на извлечение JSON).
3. Telegram-коннектор end-to-end: webhook → диалог → ответ.
4. WhatsApp-коннектор (Green API) по той же схеме.
5. Booking + handoff + notify владельцу.
6. Загрузка ClientConfig из YAML + тестовый конфиг.
7. Прогон тестовых диалогов (10 сценариев: запись, негатив, «хочу человека», вопрос вне FAQ, крупный бюджет).
8. Деплой на VPS, подключение реального клиента, сутки наблюдения, фиксы.

## Критерии приёмки

- Ответ лиду < 5 секунд.
- Квалификация заполняется по 3+ полям у ≥80% диалогов.
- Запись на слот сохраняется и подтверждается.
- Владелец получает карточку горячего лида в Telegram ≤ 1 минуты.
- Ни одной галлюцинации по ценам/услугам в тестовых сценариях.

## Уточнения реализации (v0.1.1)

1. **Логика бронирования слотов:**
   - Проверка доступности слота происходит в транзакции БД.
   - Слот блокируется на время ожидания подтверждения пользователем (TTL в Redis или статус `pending` в БД).
   - Избегание двойного бронирования одного времени разными лидами.

2. **Фильтрация WhatsApp:**
   - Обработка только сообщений типа `textMessage`.
   - Сообщения с медиа (картинки, голосовые, стикеры) игнорируются с логированием события, чтобы не тратить токены LLM и не вводить пользователя в заблуждение.

3. **Загрузка конфигурации:**
   - При старте приложения или по специальному эндпоинту `/admin/reload-configs` происходит сканирование папки `clients/`.
   - YAML файлы парсятся и сохраняются/обновляются в таблице `client_configs` в PostgreSQL.
   - Это позволяет менять настройки бизнеса без перезапуска контейнера.
